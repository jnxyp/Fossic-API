# Mod 首次收录时间

`GET /mods` 和 `GET /mods?include_modding=true` 中所有三类 Mod 新增
`mod_indexed_at: int | null`，UTC Unix 秒。

## 语义

- API 首次成功观测到该 tid 进入**默认正式索引**的后台刷新时间，不是精确发帖/移板时间。
- 沿用默认列表的筛选：本轮 DAO 返回且 fid 不在配置的 modding_fids 中。
- 首次启用后，第一个成功 Mod 快照中的正式帖子作为历史基线，永久保留 null。
  首轮只有 Modding 或空列表也完成基线初始化，之后的新正式条目记录当轮时间。
- Modding 不生成新时间；此前正式收录过的帖子退回 Modding 时，在完整视图中保留原时间。
- 原创、汉化、搬运一律记录。tid 是唯一身份；编辑、改 mod_id/版本/类型/附件、移出再返回、重启都不重置。
- 不推断历史，不扫描日志，不改 Discuz 表或发帖/移板逻辑。
- 前端自行决定七天窗口及原创类型高亮；后端不返回到期时间或高亮布尔，不改变排序/评分。

## 持久化和一致性

复用 DOWNLOAD_STATS_DB_PATH 指定的现有 SQLite，新增两个独立表：

| 表 | 内容 |
|---|---|
| mod_index_state | singleton=1，initialized_at；首个成功快照的一次性基线完成标记 |
| mod_index_times | tid 主键、indexed_at 可空；NULL 行与无行有意区分 |

启动时在现有 initialize 事务中创建扩展表；此时**不**创建基线完成标记。
后台刷新沿用同一个 BEGIN IMMEDIATE：收录观测 → 下载统计 → 汇总/评分 →
完整模型校验、全部响应编码 → COMMIT → 发布内存快照。
编码、校验或事务失败不提交时间、基线标记或部分下载增量，并保留旧快照。
提交后、发布前崩溃时，下一轮沿用已经提交的首次时间。
请求仍直接返回预编码 bytes，不增加请求SQL、SQLite访问、序列化或定时任务。

## 升级、备份和回退

这是原 schema v1 的**加法扩展**，不改变原表或 user_version=1。
旧版本仅检查其原有表和版本，不拒绝额外表，因此可以保留同一数据库回退代码，
不需要恢复旧库或删除新表，不丢失期间新增下载统计。
旧代码不记录收录时间；回退期间首次进入的帖子只能在重新启用新版后按观测时间记录。
原来的 NULL 基线和已记录时间均保留，不能在回退/重启时清空数据库。

现有 sqlite backup API 自动包含这两个表及 WAL 已提交内容，继续沿用
[下载统计备份与恢复](download-statistics.md)。部署仍需另行授权；本功能PR不改生产或备份计划。

## 验证

专项测试覆盖首次空/Modding/正式基线、三类型、直入/转入、编辑/移出/重入、
重开持久库、分批读取、严格字段/OpenAPI、失败回滚、v1加法升级及一致性备份恢复。
现有全量回归继续检查请求热路径无SQL和编码、全部快照原子性及下载统计算法。
本地论坛模拟环境的实际 MySQL/API 验证结果记录在PR说明，不把合成注入当成完整编辑器工作流验收。
